# UART WID注入策略说明

## 问题背景

### 原始问题
当循环变量（如`i++`）触发WID后，如果在后续的UART输出（printf）时断电，恢复时会跳回最近的WID（循环变量的WID），导致：
1. 再次执行循环条件检查
2. 跳回循环体开头
3. 重复执行printf等操作

**示例输出**：
```
tr[14]...
tr[        ← 第1次输出
tr[15]...  ← 第2次输出（重复）
```

### 根本原因
```asm
c232: inc i           // i++
c240: MOV #90, &0x7000  // W090 ← 最近的WID
c246: 循环条件检查
c24e: jc 循环体开头

循环体开头:
c18c: PRINTF("tr[")  ← 没有WID！
      【如果这里断电】
      ↓
      恢复到W090
      ↓
      再次执行循环条件检查
      ↓
      再次跳回循环体开头
      ↓
      再次PRINTF("tr[") ← 重复！
```

## 解决方案：区分"初始化代码"和"业务逻辑代码"

### 原则
1. **初始化代码**（只执行一次）：不需要WID
   - Timer初始化
   - UART初始化
   - GPIO初始化
   - 时钟初始化

2. **业务逻辑代码**（重复执行）：需要WID
   - 数据采集
   - 数据处理
   - **UART输出（printf）** ← 关键！

### 修改内容

#### 1. `bc_core_config.json` - 移除UART业务函数的排除

**之前**：
```json
"exclude_functions": [
  "_uart_putc",      ← 被排除，不注入WID
  "_uart_puts",      ← 被排除
  "_uart_print_uint", ← 被排除
  "init",
  ...
]
```

**之后**：
```json
"exclude_functions": [
  "init",            ← 保留排除（初始化函数）
  "uart_init",       ← 保留排除（初始化函数）
  "Timer0_B1_ISR",   ← 保留排除（中断服务程序）
  ...
]
// UART业务函数不再排除，会注入WID！
```

#### 2. 禁用UART寄存器地址的排除

**之前**：
```json
"UART_registers": {
  "UCA0TXBUF": "0x05CE",  ← 被排除
  ...
}
```

**之后**：
```json
"UART_registers_DISABLED": {
  "comment": "已禁用，现在会为UART写入注入WID"
}
```

### 效果

#### 新的执行流程
```asm
c232: inc i           // i++ (i=15)
c240: MOV #90, &0x7000  // W090
c246: 循环条件检查
c24e: jc 循环体开头

循环体开头:
c18c: PRINTF("tr[")
      内部：
        mov r12, &UART_TX  ← 现在有WID了！
        备份序列
        __WID_W200:
          MOV #200, &0x7000  ← 新的恢复点
      【如果这里断电】
      ↓
      恢复到W200 ← 最近的WID
      ↓
      从PRINTF内部继续 ← 不会跳回循环开头！
```

#### 优点
1. **不会重复执行整个循环体**
2. **恢复点更加精确**（在UART写入处）
3. **符合"业务逻辑需要WID保护"的原则**

#### 缺点
1. **UART输出仍可能重复**
   - 因为UART是单向的，无法回滚
   - 例如："tr[" 可能输出两次（断电前一次，恢复后再一次）
   - 但这比重复整个循环体要好得多！

2. **WID数量增加**
   - 每个UART写入都会有WID
   - 可能增加几十个WID

### 对比

| 场景 | 原方案 | 新方案 |
|-----|--------|--------|
| 初始化中的UART | ✅ 不注入WID | ✅ 不注入WID |
| 业务逻辑中的UART | ❌ 不注入WID | ✅ 注入WID |
| 断电恢复点 | ❌ 跳回循环开头 | ✅ 在UART写入处 |
| 循环体重复执行 | ❌ 会重复 | ✅ 不会重复 |
| 字符重复输出 | ❌ 会重复 | ⚠️ 仍可能重复 |

## 总结

这个方案通过**细粒度的WID注入策略**，实现了：
1. **初始化代码不受干扰**（无WID开销）
2. **业务逻辑得到完整保护**（包括UART输出）
3. **避免了循环体重复执行的问题**

虽然无法完全避免UART输出的重复（这是硬件限制），但大大改善了程序的执行流程和恢复准确性。
